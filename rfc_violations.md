# RFC violations

Проверка выполнена относительно `docs/rfc.md`.

## Критично

### 1. `replanTail()` может повторно отправить уже доставленный кусок, если исходно был разрезан один большой блок
- В `split-blocks-soft` и `forced-plain-text` все фрагменты одного и того же блока получают одинаковый диапазон всего блока: `packages/message-chunker/src/planner.js:205`, `packages/message-chunker/src/planner.js:780`, `packages/message-chunker/src/planner.js:789`.
- Затем `replanTail()` берёт только `sourceRange.start.path[0]` и перепланирует хвост с начала top-level блока: `packages/message-chunker/src/replan.js:51`.
- В результате отказ на 2-м чанке длинного параграфа или списка приводит к перепланированию с начала этого же параграфа/списка и повторной отправке уже доставленного префикса.
- Это нарушает требования RFC о том, что `SourceRange` должен адресовать логический диапазон внутри нормализованного IR и что уже доставленный префикс не должен пересылаться повторно: §§6.6, 6.10, 17.1, 18.1, 19.7.

## Высокая важность

### 2. Сплит параграфа не всегда ищет максимально длинный допустимый префикс
- `splitInlineOnce()` останавливается на границе inline-узла, если следующий узел не помещается целиком; частично использовать текст из этого же узла она уже не пытается: `packages/message-chunker/src/planner.js:281`.
- Пример: для `**A** verylongword` при бюджете `10` первый чанк получается только `A` / `<b>A</b>`, хотя RFC требует искать самый длинный префикс, не превышающий бюджет.
- Это расходится с правилами greedy/max-prefix split: §§13.2, 13.3, 14.1.

### 3. Rich HTML renderer генерирует запрещённый атрибут `class`
- Для fenced code block с языком генерируется `<pre><code class="language-..."></code></pre>`: `packages/message-chunker/src/renderer-html.js:58`.
- RFC v1 разрешает только transport-safe subset без произвольных атрибутов: §11.1.
- Такой HTML может быть отвергнут транспортом, для которого и вводился ограниченный subset.

## Средняя важность

### 4. Диагностика не фиксирует деградацию для unsupported markdown
- Таблицы принудительно опускаются до обычного текста уже на этапе парсинга: `packages/message-chunker/src/parser.js:9`.
- Но `hadDegradation` выставляется только при смене стратегии/режима и не учитывает деградацию при нормализации unsupported constructs: `packages/message-chunker/src/planner.js:810`.
- Это нарушает прямое требование RFC фиксировать такую деградацию в диагностике: §§14.6, 20.

### 5. При очень маленьком бюджете код-блок может быть разбит на несбалансированные fenced fragments
- В `forced-plain-text` сначала делается попытка разбить код-блок с балансировкой fence, но при неудаче включается fallback «как сырой текст»: `packages/message-chunker/src/planner.js:619`.
- Для маленьких бюджетов это даёт чанки вроде `` ``` `` и `a\n````, то есть fence оказываются несбалансированными.
- RFC требует, чтобы при разбиении code block в plain-text / forced-plain-text каждый чанк оставался сбалансированным fenced block: §§11.4, 14.5.
