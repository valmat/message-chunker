# Code issues

## Критично

### 1. Нет точного адресования внутри разрезанного блока
- Корневая причина: `PlannedChunk.sourceRange` вычисляется только по границам top-level блоков и одинаков для всех частей одного split-блока: `packages/message-chunker/src/planner.js:205`, `packages/message-chunker/src/planner.js:780`, `packages/message-chunker/src/planner.js:789`.
- Из-за этого `replanTail()` не умеет возобновляться с точного места внутри параграфа/списка/цитаты и дублирует уже доставленный текст: `packages/message-chunker/src/replan.js:51`.
- Это не просто неточность метаданных, а дефект поведения: повторная отправка уже коммитнутого префикса.

## Высокая важность

### 2. `splitInlineOnce()` заполняет чанк не максимально плотно
- Если текущий inline-узел не влезает целиком, функция немедленно режет на его границе и не использует остаток бюджета, даже если внутри узла можно безопасно взять часть текста: `packages/message-chunker/src/planner.js:288`.
- Последствия: больше чанков, менее стабильная упаковка, более ранняя деградация стратегии/режима.

### 3. Генерация HTML для code block повышает риск transport reject
- `renderCodeBlockHtml()` добавляет `class="language-*"`, хотя остальной renderer старается держаться минимального safe subset: `packages/message-chunker/src/renderer-html.js:58`.
- Для Telegram-like транспорта это лишний источник `invalid-markup`/reject без практической пользы для v1.

## Средняя важность

### 4. Fallback для маленького бюджета ломает fenced code block
- Если budget меньше overhead fenced блока, код переходит к raw-text split и теряет балансирующие fence: `packages/message-chunker/src/planner.js:634`.
- Это делает output менее предсказуемым и ухудшает читаемость в самом аварийном сценарии, где библиотека должна быть максимально надёжной.

### 5. Диагностика занижает количество деградаций
- `hadDegradation` не знает о деградации, произошедшей во время normalize/parse unsupported markdown: `packages/message-chunker/src/planner.js:810`.
- В логах и тестах такие кейсы выглядят «чистыми», хотя формат уже был понижен.

## Низкая важность

### 6. `replanTail()` принимает `rejectReason`, но полностью его игнорирует
- Поле есть в контракте, но не используется и даже не валидируется: `packages/message-chunker/src/replan.js:27`.
- Это снижает ценность API: невозможно отличить опечатку в причине reject от реально поддержанного сценария, а будущая логика ветвления по причинам уже частично «задекларирована», но не реализована.
