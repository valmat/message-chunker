# Known limitations v1

Осознанные ограничения текущей версии. Для каждого описана мотивация решения "знаем, но не делаем".

## 1. Диагностика не фиксирует деградацию unsupported markdown

**Суть**: таблицы отключены на уровне парсера (`md.disable('table')`), raw HTML и изображения преобразуются в текст на этапе нормализации. Поле `hadDegradation` в диагностике не отражает эти потери — оно фиксирует только деградацию стратегий/режимов при планировании.

**Почему не делаем**:
- Деградация unsupported конструкций происходит до pipeline планирования, в normalizer
- RFC §14.6/§20 формулирует требование к диагностике в контексте стратегий планирования
- Для отслеживания нужен обратный канал из normalizer в planner (усложнение архитектуры)
- Практическая ценность низкая: вызывающий код и так знает, что модуль не поддерживает таблицы — это задокументировано в API

**Когда пересмотреть**: если появятся конструкции, поддерживаемые частично (например, таблицы рендерятся упрощённо), и диагностика станет нужна для принятия решений на стороне вызывающего кода.

## 2. Несбалансированные fenced code blocks при экстремально маленьком бюджете

**Суть**: если бюджет меньше overhead fenced block (```` ```lang\n...\n``` ````), balanced split невозможен. В `forced-plain-text` включается fallback — raw-text split без балансировки fence.

**Почему не делаем**:
- Это аварийный fallback для нереалистично маленьких бюджетов (< ~10 символов)
- Альтернатива — не отдавать контент вообще, что хуже: RFC §19.6 требует, чтобы `forced-plain-text` всегда возвращал план для любого непустого текста
- При таком бюджете любой вывод будет нечитаемым, балансировка fence не улучшит UX

**Когда пересмотреть**: если появится реальный transport с бюджетом < 20 символов (маловероятно).

## 3. Unicode splitting — surrogate-pair safe, но не grapheme-cluster safe

**Суть**: `unicodeSafeSplit` гарантирует целостность суррогатных пар (UTF-16), но не grapheme clusters. ZWJ-последовательности (например, 👨‍👩‍👧‍👦) и комбинирующие символы (e + U+0301 → é) могут быть разрезаны.

**Почему не делаем**:
- RFC §6.7 требует "Unicode-safe boundaries" — в контексте UTF-16 это суррогатные пары
- Полная grapheme segmentation требует `Intl.Segmenter` (доступен в Node.js 16+, но значительно медленнее)  или тяжёлую библиотеку
- Разрезание ZWJ-последовательности не создаёт невалидный Unicode — просто отображение отличается
- Практическое влияние минимально: разрез внутри grapheme cluster возможен только в `forced-plain-text` при тексте без пробелов

**Когда пересмотреть**: если пользователи сообщат о проблемах с emoji-heavy контентом или если модуль будет использоваться для языков с обязательными комбинирующими символами (арабский, деванагари).

## 4. `rejectReason` принимается, но не влияет на логику

**Суть**: `ReplanTailRequest.rejectReason` определён в контракте (RFC §18.2) со значениями `too-long` и `format-rejected`, но в v1 обработка одинакова для обеих причин.

**Почему не делаем полную реализацию**:
- В v1 единственная разумная реакция на оба типа reject — эскалация стратегии, что и происходит через `nextStrategy`
- Разное поведение для `format-rejected` (например, немедленный переход в plain-text) — это оптимизация, а не корректность
- Поле присутствует в контракте для forward compatibility, чтобы не ломать API при добавлении логики в v1.1

**Что сделано**: добавлена валидация допустимых значений `rejectReason`.

**Когда пересмотреть**: при реализации умной стратегии для `format-rejected` (например, пропуск rich-html стратегий и прямой переход в plain-text).
