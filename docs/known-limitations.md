# Known limitations v1

Осознанные ограничения, уже принятые упрощения v1 и несколько оставшихся gaps между текущей реализацией и обновлённым RFC.

## 1. `SourceRange` неточен внутри split-блока

**Суть**: при разбиении длинного параграфа, списка, цитаты или code block на несколько чанков все части одного top-level блока получают один и тот же `sourceRange`, фактически указывающий на весь исходный блок.

**Последствие**: `replanTail()` умеет возобновляться только с начала top-level блока. Если reject произошёл на 2-м или 3-м фрагменте одного длинного блока, уже доставленный префикс может попасть в tail повторно.

**Статус**: критичное известное ограничение v1. План работ вынесен в `docs/refactoring-sourcerange.md`.

## 2. Unsupported markdown может деградировать без специального флага в диагностике

**Суть**: таблицы, raw HTML и другие unsupported конструкции могут быть понижены до текста на этапе parse/normalize, а `diagnostics.hadDegradation` при этом может остаться `false`.

**Продуктовое решение**:
- для v1 это допустимо;
- отдельная обязательная реакция продукта на такой случай не требуется;
- максимум — документация и optional logging.

**Статус**: accepted limitation v1, не blocker для следующей итерации.

## 3. Текущая реализация ещё не валидирует новый минимальный budget из RFC

**Суть**: в RFC v1 теперь зафиксировано, что supported transport profile должен иметь `safeTextBudget >= 200` (в UTF-16 code units). Код пока ещё не синхронизирован с этим правилом.

**Почему это важно**:
- unreasonable budgets больше не считаются штатным сценарием для planner;
- профиль с меньшим budget должен отклоняться как invalid transport profile.

**Статус**: gap между кодом и обновлённым RFC; требуется простая синхронизация валидации.

## 4. Unicode splitting — surrogate-pair safe, но не grapheme-cluster safe

**Суть**: `unicodeSafeSplit` гарантирует целостность суррогатных пар (UTF-16), но не grapheme clusters. ZWJ-последовательности и комбинации base char + combining mark могут быть разрезаны.

**Продуктовое решение**:
- для v1 этого достаточно;
- отдельной продуктовой реакции не требуется.

**Статус**: accepted technical limitation v1.

## 5. Код ещё не синхронизирован с новым контрактом `rejectReason`

**Суть**: по обновлённому RFC модуль различает только `too-long` и `invalid-markup`. Прочие transport-level ошибки остаются за интеграцией. Текущая реализация и typedef-часть кода пока ещё не приведены к этому решению.

**Что это означает practically**:
- нужно выровнять RFC, typedef, README и runtime-валидацию;
- ошибки транспорта вроде 401/429/5xx не должны описываться как каноническая часть контракта самого модуля.

**Статус**: контрактное решение принято, кодовая синхронизация остаётся на следующую итерацию.

## 6. Реализация rich-html code block временно отстаёт от обновлённого RFC

**Суть**: RFC теперь явно разрешает сохранять language info fenced code block через `class="language-*"` на `<code>` внутри `<pre>`, но текущая реализация renderer этого ещё не делает.

**Продуктовое решение**:
- language info сохранять нужно;
- это важная часть rich representation, а не случайный бонус.

**Статус**: gap между кодом и обновлённым RFC; нужно вернуть поддержку `<pre><code class="language-LANG">...</code></pre>` и синхронизировать тесты.

## 7. Policy после reject намеренно остаётся на клиенте

**Суть**: библиотека не должна хардкодить orchestration после reject. Она предоставляет ручки (`preferredMode`, `nextStrategy`, `transport.safeTextBudget`, diagnostics), а решение о том, что менять после reject, принимает интеграция.

**Продуктовое решение**:
- для `too-long` клиент может уменьшать budget, повышать strategy или комбинировать оба подхода;
- для `invalid-markup` типичный сценарий — перевод tail в `plain-text`, но orchestration всё равно остаётся на стороне клиента;
- transport-level ошибки вне модульной классификации вообще не входят в contract policy библиотеки.

**Статус**: это уже не открытый вопрос, а зафиксированное архитектурное решение.


## 8. Iterator / streaming API остаётся возможным будущим расширением

**Суть**: для некоторых интеграций более естественным мог бы быть API в виде iterator/stream, а не готового массива `chunks[]`.

**Продуктовое решение**:
- v1 остаётся на каноническом контракте `DeliveryPlan { chunks: PlannedChunk[] }`;
- идея iterator/streaming API признана полезной, но не рассматривается как задача текущей итерации.

**Статус**: future extension, не blocker для v1.
