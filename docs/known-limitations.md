# Known limitations v1

Осознанные ограничения и открытые вопросы текущей версии. Для каждого описано, что именно сейчас происходит и почему это ещё не доведено до идеального состояния.

## 1. `SourceRange` неточен внутри split-блока

**Суть**: при разбиении длинного параграфа, списка, цитаты или code block на несколько чанков все части одного top-level блока получают один и тот же `sourceRange`, фактически указывающий на весь исходный блок.

**Последствие**: `replanTail()` умеет возобновляться только с начала top-level блока. Если reject произошёл на 2-м или 3-м фрагменте одного длинного блока, уже доставленный префикс может попасть в tail повторно.

**Почему ещё не исправлено**:
- Для корректного решения нужно адресование не только по `path[0]`, но и внутри leaf-нод через `offsetUtf16`
- Потребуется поменять контракт между split-функциями, финализатором чанков и `replanTail()`
- Это большой рефакторинг, затрагивающий planner, replan и тесты golden/property

**Статус**: критичное известное ограничение v1. План работ вынесен в `docs/refactoring-sourcerange.md`.

## 2. Диагностика не фиксирует деградацию unsupported markdown

**Суть**: таблицы отключены на уровне парсера (`md.disable('table')`), raw HTML и изображения преобразуются в текст на этапе нормализации. Поле `hadDegradation` в диагностике не отражает эти потери — оно фиксирует только деградацию стратегий/режимов при планировании.

**Почему не делаем сейчас**:
- Деградация unsupported конструкций происходит до pipeline планирования, в normalizer
- Для корректного отражения нужен обратный канал из normalizer в planner
- Это усложняет архитектуру ради сравнительно слабого диагностического сигнала

**Что это означает practically**: unsupported markdown может уже быть понижен до текста, а `diagnostics.hadDegradation` при этом останется `false`.

**Когда пересмотреть**: если диагностика начнёт использоваться для бизнес-решений, а не только для отладки и тестов.

## 3. Несбалансированные fenced code blocks при экстремально маленьком бюджете

**Суть**: если бюджет меньше overhead fenced block (например, меньше длины ```` ```\n\n``` ````), balanced split невозможен. В `forced-plain-text` включается аварийный fallback — raw-text split без балансировки fence.

**Почему не делаем сейчас**:
- Это аварийный сценарий для нереалистично маленьких бюджетов
- Альтернатива — не вернуть план вообще, что хуже для общей надёжности модуля
- При таком бюджете читаемость уже почти недостижима независимо от формы вывода

**Что это означает practically**: в редком edge-case чанк с code block может выглядеть как часть fence, а не как полноценный fenced block.

## 4. Unicode splitting — surrogate-pair safe, но не grapheme-cluster safe

**Суть**: `unicodeSafeSplit` гарантирует целостность суррогатных пар (UTF-16), но не grapheme clusters. ZWJ-последовательности и комбинации base char + combining mark могут быть разрезаны.

**Почему не делаем сейчас**:
- В v1 целевой обязательный минимум — не ломать суррогатные пары
- Полная grapheme segmentation требует более тяжёлой логики и дополнительных зависимостей/стоимости
- Практически это проявляется только в самом жёстком fallback

**Что это означает practically**: Unicode остаётся валидным, но отдельные emoji/комбинированные символы могут отображаться неидеально после forced split.

## 5. `rejectReason` валидируется не в тех терминах, что RFC и типы

**Суть**: сейчас `replanTail()` принимает `too-long | format-rejected`, тогда как RFC и typedef `RejectReason` описывают `too-long | invalid-markup | transport-reject`.

**Почему это проблема**:
- Это реальное расхождение между реализацией, типами, документацией и спецификацией
- Пользователь API может передать значение, формально допустимое по типам/RFC, и получить runtime-ошибку
- Наоборот, значение `format-rejected` сейчас принимается кодом, но не описано в RFC как каноническое

**Что нужно решить**:
- либо вернуть реализацию к терминам RFC,
- либо обновить RFC, typedef и README единообразно.

**Статус**: открытый контрактный вопрос, не просто limitation поведения.

## 6. Реализация rich-html code block временно отстаёт от обновлённого RFC

**Суть**: RFC теперь явно разрешает сохранять language info fenced code block через `class="language-*"` на `<code>` внутри `<pre>`, но текущая реализация renderer этого ещё не делает.

**Почему это важно**:
- language info у fenced block — полезная часть rich representation
- после обновления RFC это уже не спорная интерпретация, а ожидаемое поведение safe subset

**Что это означает practically**:
- fenced block вроде ```` ```bash ```` сейчас всё ещё рендерится без `language-bash`
- это уже не limitation спецификации, а gap между кодом и обновлённым RFC

**Что нужно сделать**: вернуть поддержку `<pre><code class="language-LANG">...</code></pre>` в rich-html renderer и синхронизировать тесты.
